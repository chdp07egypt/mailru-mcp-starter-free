# Что пришлось проверить на практике

1. **Браузер и IMAP — разные пути.** Доступ к веб-входу Mail.ru/VK может быть ограничен в среде агента. В этой реализации используется штатный IMAP с TLS; браузерные ограничения не отключаются и сертификаты не подменяются. Пароль внешнего приложения обязателен.
2. **Доступ к репозиторию и доступ к почте — разные разрешения.** Render должен видеть GitHub Fork, а почтовый сервер — принимать пароль внешнего приложения. Успешный deploy не доказывает IMAP login.
3. **Google login хостинга не заменяет OAuth приложения.** Нужен свой Web application Client с собственным callback.
4. **Инструкция/skill и подключённый MCP — разные результаты.** Проверяйте реальные команды и вызовы, а не наличие карточки плагина.
5. **Scopes необходимо планировать до первого подключения.** Добавление write-команды не меняет выданные read-only токены. В публичном шаблоне единый `mail.access` с изначальным явным согласием на все пять действий.
6. **OAuth проверяется в браузере целиком.** Неверная Referrer Policy может убрать Origin формы, а слишком узкая CSP — заблокировать переход на разрешённый ChatGPT callback. Включены регрессионные проверки этих настроек.
7. **MOVE проверяется с двух сторон.** После действия письмо должно исчезнуть из источника и появиться в назначении с новым UID. Ошибка сети после отправки команды не означает, что действие не выполнено.
8. **Free-хостинг имеет режим сна.** Состояние незавершённого входа теряется при перезапуске. OAuth после deploy начинают заново; старую callback-страницу не переиспользуют.

Практическая проверка исходной личной интеграции: получены папки, выполнены поиск и чтение, выбранное письмо перемещено в корзину, обе папки проверены. Публичная адаптация прошла автоматические тесты; чужие credentials и новый deploy каждый пользователь проверяет отдельно.
